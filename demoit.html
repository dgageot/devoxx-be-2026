Tool call permissions

Choose what runs and what needs approval

Look up factsallow → run
Practice a matchask → confirm
runtime:
  safety: strict
permissions:
  allow:
    - pokemon_retrieve
  ask:
    - spar_team

Optional four-minute detour; skip straight to structured output if short on time. No live run needed.

We just gave the agent a business API tool. Which calls should run automatically? Strict mode asks for every call unless an allow rule matches; here we allow fact lookups and ask before practice.

This is an illustrative permissions excerpt, not a full config or a change to 10-sparring.yaml. For this policy, use --safety strict and retain allow entries for the other discovery tools. The existing sparring demo uses restricted mode; the next structured-output demo is unchanged.

Permission order is deny, then allow, then ask. An allow rule wins over ask; a broad allow rule in agent or user policy can silence this ask. Avoid allow: ["*"]. Deny takes priority over both.

YAML ask is not the same as a mandatory tool guard: it yields to user-selected balanced, restricted or autonomous modes. --yolo can bypass YAML ask. An interactive always-allow grant can also silence later prompts.

Approve the practice call and the tool runs; reject it and there is no practice result. Sparring is stateless: it does not submit an arena entry or award leaderboard points. Confirmation here is a teaching choice, not a claim that practice is destructive.

Do not use an interactive ask as an unattended approval workflow. In strict headless runs there is no interactive approver, so the call is declined.

Permissions are not a sandbox. Tool content and attachments are data, not authority. Sparring still checks TEAM-1, SPECIES-1, BUDGET-1, COVERAGE-1 and DATA-1 independently. Approval does not replace evidence checks. Later, a local match requires an explicit user request, and FAIR-1 keeps entries sealed until judging.

Business parallel: auto-approve catalog queries; ask before running a business operation. The service still checks identity, authorization and business rules.

03Prove

An agent improves the prompt

Inspect failures → edit a candidate → rerun the same evals

Optional live detour; skip straight to the final-exam boundary if short on time. This dedicated optimizer is a development agent, not a coordinator for building teams. It edits a disposable copy of 11-builder.yaml and invokes the native eval CLI; there is no built-in optimizer tool.

Run from the repository root with the same Docker Desktop, prepared PokéAPI, healthy arena and provider access as the previous evals. The shell asks for approval in strict mode: inspect each command before allowing it. Each full eval uses a 600-second shell timeout. Do not use --yolo or an always-allow shell grant.

The agent creates a unique .state/prompt-loop/run.* workspace and copies the builder, team-building.md and eval-setup.sh together. Native eval mounts the candidate's parent at /configs, so omitting the support files would break setup. The source builder and captured baselines remain untouched.

First measure a fresh baseline: the same five development cases, five repeats, judge and unchanged model/tools. Then form one hypothesis per attempt and change only agents.root.instruction. Save each attempt's YAML and native results separately; compare with the best accepted Sessions JSON via --baseline. That native file contains summary metrics and per-session eval results. A nonzero exit can indicate regression or infrastructure failure: inspect the report rather than retrying until green.

Keep an edit only if it passes more repetitions and the native gate reports no regression; inspect per-case failures, cost and latency too. Stop at three candidate runs or 25/25. If nothing improves, keep the baseline. These are live results, not a captured claim of prompt-only gains or guaranteed reliability.

Filesystem tools read only the source/support files, development cases and workspace, and write only within the workspace. Those limits do not sandbox shell access: held-out exclusion, prompt-only edits and immutable raw results also depend on instructions and human command review. Do not read credentials or frozen old/ examples.

The optimizer's budget caps its own metered model calls, not the child eval processes or their judge calls; up to four repeat-5 suites incur separate spend. External commands may outlive a timeout or interruption. Stop only processes owned by this run and retain incomplete evidence for review.

Do not weaken tests, evidence checks or rules: TEAM-1, SPECIES-1, BUDGET-1, COVERAGE-1, DATA-1 and FAIR-1 remain unchanged. Failed/conflicting evidence requires human review (DATA-1); teams stay sealed (FAIR-1). No entry, tournament or state reset is authorized. A human reviews and freezes the chosen config before running held-out cases separately; the optimizer never reads those cases.

04Serve

Not every request needs the same model

Keep Sol for the builder. Try Luna for coordination and practice.

Lower cost or latency? Measure the whole request. Keep the quality bar.

Optional five-minute detour after wiring the specialists; skip straight to exposing the builder as a service. The default 12-team.yaml run and subsequent service configs are unchanged.

We already have three roles. Does coordinating the request or reporting a measured practice result need the same model as choosing a constrained team? Hypothesis: reserve Sol for the builder and use Luna for the coordinator and coach to lower cost or latency without losing correctness.

This is a fixed model assignment by role, not an automatic complexity router, parallel execution or a fallback mechanism. Both flavors use the same agents, instructions, tools and handoffs; both named models disable thinking. The comparison baseline is all-strong, not the preceding default run, which already uses different models.

Run the top terminal to completion, then the bottom, using fresh sessions and the identical request. Each terminal waits for Enter. Click its green button (or use Command-Enter) to maximize the active terminal for the live run and cost inspection, then restore it to compare the YAML. The source tabs show model assignments and definitions; Full file exposes the complete runnable config. Open /cost in each TUI to inspect the session's estimated cost and its agent/model breakdown. Compare the whole request, not just one cheap call. Verify pricing is available for both models; an unknown or zero estimate is not evidence of a free run. Provider billing is authoritative.

For elapsed time, rehearse the identical commands with time docker agent run --exec instead of the TUI. Measure process start to exit, including CLI startup and tools; do not time an interactive session's human pauses or claim the TUI is a stopwatch. Repeat both variants at least five times, alternate their order and report medians with success counts. Provider latency and caching can affect the comparison.

Inspect correctness before price: three distinct Generation I default species, at most 1000 stats and at least one Water member (TEAM-1, SPECIES-1, BUDGET-1, COVERAGE-1). Each final member needs successful lookup evidence. The coach must receive the exact chosen team and return the actual beginner result, including a loss. Missing or conflicting evidence requires human review (DATA-1). Also inspect duplicate work: extra handoffs, repeated lookups or practice calls can erase any savings.

No measured savings or speedup are claimed here. Cheaper tokens do not guarantee a cheaper task, and multiple agents can be slower than one. Keep the mixed assignment only if repeated checks retain quality and improve the chosen cost or latency metric. The builder eval suite expects structured JSON; this coordinator returns prose, so it needs its own eval assertions before a production decision.

Only stateless practice is requested. Neither flavor has entry or tournament tools; no local match is authorized. FAIR-1 still keeps arena entries sealed until backend judging.

04Serve

See the agent's trace

Optional live detour; skip straight to MCP if short on time. Prepare the digest-pinned local Jaeger image before the talk: docker compose -p devoxx-tracing -f compose.tracing.yaml pull. No builds or pulls happen on stage.

Start terminals top to bottom: Jaeger, traced server, then client. Wait for Jaeger's viewer and the server's listening message before sending the request. The separate chat port 8082 avoids colliding with the previous application's server on 8080.

The endpoint enables OTLP/HTTP export to Jaeger on loopback 4318; --otel opts into tracing. Message content capture is explicitly false for this listener. Jaeger's viewer is on 16686. Both are local, not public services.

After the client completes, allow at least five seconds for batched spans to arrive. Choose the docker-agent service and click Find Traces; if the service is absent, refresh the embedded browser. Open the newest trace. Expand model and tool spans; compare durations, token usage when reported, lookup counts and errors. The search page does not auto-refresh results.

Trace hierarchy and timings are live observations, not a pre-captured score or a guarantee. An instrumented application can propagate trace context into the chat server; our Python client does not. PokéAPI and the arena need their own instrumentation to expose service-internal work.

The viewer helper stays attached to the first terminal. Ctrl-C or leaving the slide closes it and removes only the container created by that invocation. Docker detachment alone would not stop Jaeger, so the helper explicitly cleans up on terminal hangup. Occupied ports fail without stopping their owners. Jaeger stores traces in memory: leaving the slide discards them. A hard process kill or Docker outage can prevent cleanup and needs human review.

Jaeger accepts traces only. This Docker Agent build also exports metrics/logs to the same base endpoint; those exports can report unsupported-endpoint errors without invalidating trace export. Do not assume OTEL_METRICS_EXPORTER=none disables this build's explicitly constructed exporters.

Prompt/response content and tool arguments/results are omitted by default and capture is explicitly disabled here. Span metadata and error descriptions still need appropriate access and retention controls. Failed/conflicting evidence requires human review (DATA-1); sealed teams remain governed by FAIR-1. No entry or local match is requested by this demo.

Ship the exact agent you evaluated

OCI artifacts: version the configuration, deploy by digest

Freeze

Chosen flavor and reviewed guidance

Evaluate

Keep results and runtime versions

Publish

Versioned tag → immutable digest

docker agent share push release.yaml myorg/team-builder:v1
docker agent serve chat myorg/team-builder@sha256:<digest> \
  --listen 127.0.0.1:8080

Optional four-minute detour; skip straight to the leaderboard if short on time. Static examples only: release.yaml, myorg and <digest> are placeholders, not checked-in files or a published release. No registry write, model call or service startup is needed on stage.

Compose packages the execution environment; an OCI agent artifact distributes the configuration. Freeze the reviewed release inputs, evaluate them, publish, then verify the retrieved artifact and its dependencies before promotion. Keep the full OCI manifest digest with the release evidence and deploy that digest, not a moving tag. A digest identifies bytes, not quality or publisher trust; it does not certify a passing eval.

For example, docker agent debug config agents/11-builder.yaml checked-totals can resolve the chosen flavor into a release YAML before evaluation. With a flavor supplied, debug config bakes in the patches and removes the flavors section; share push itself has no --flavor option. Review the resolved file and evaluate those release inputs. Do not assume 11-builder.yaml results certify the different 13-service.yaml builder, its container flavor or a newly transformed release.

The artifact stores the configuration as YAML, not a container image or a workspace archive. instruction_file contents are inlined when pushing, but add_prompt_files remain external path references. Our builders need team-building.md; the served builder also loads AGENTS.md. Supply the exact reviewed files in a versioned read-only workspace, as in Compose, and verify their hashes and working-directory resolution. Missing prompt files can be silently skipped. Alternatively, deliberately inline reviewed guidance into the release configuration before evaluating it; that transformation needs review and fresh evals, not a claim that push bundles it automatically.

Eval cases, eval-setup.sh, raw results, binaries such as jq/awk, OpenAPI specs, model weights and backend data are not bundled by share push. Retain an external release record with source revision, selected flavor, support-file hashes, cases and raw result paths, CLI/runtime image version or digest, model and judge settings, spec/backend evidence versions and the full OCI manifest digest. The publication command does not automatically attach eval evidence.

Tags, even v1, can be overwritten. Resolve the published tag with registry tooling and copy the full manifest digest into <digest>; do not use the local YAML checksum or the signature's YAML-layer digest as the registry reference. Inspect and validate the retrieved configuration with the pinned support workspace, then run the release evals before promoting that digest. Later model, tool, environment or policy overrides mean a different effective agent and need validation.

Registry access may require login and network access; provider credentials still come from the runtime. Never place secrets in the YAML: it is published in clear, even with share push --encrypt. Signing is a separate provenance check, not proof of eval success. Do not read credential files or publish anything during this detour.

The serve command illustrates replacing the local YAML with a registry reference; it is not an additional listener to start beside the previous 8080 service. Stop only an owned listener if deliberately rehearsing the replacement. Keep access on loopback and provision the same reviewed guidelines and backend services; the later leaderboard demos are unchanged.

Immutable config bytes do not freeze hosted model behavior or live tool responses. Missing or conflicting evidence still requires human review (DATA-1); current backend rules remain authoritative and FAIR-1 keeps teams sealed until judging. Distribution grants no entry authority, and this slide requests no local match or tournament.
